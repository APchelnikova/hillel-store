# Hillel Store API

## Товари та власники

**Підхід:** поле `products.owner_id` — зовнішній ключ на `users.id`. Будь-який автентифікований користувач може створити товар і стає його власником. `owner_id` береться з JWT, а не з тіла запиту. Редагувати, видаляти товар і додавати йому атрибути може лише власник, інакше 403.

**Чому не прапорець `is_owner`:**

- Власність — це зв'язок із конкретним товаром, а не властивість користувача: для перевірки «чий це товар» `owner_id` потрібен у будь-якому разі, тож прапорець був би зайвим полем.
- «Чи є користувач власником» легко обчислити за його товарами. Окреме поле дублювало б цю інформацію і могло б застаріти.
- Зовнішній ключ гарантує, що товар не посилається на неіснуючого користувача.

Якщо знадобиться модерація продавців, можна додати роль `seller` у вже наявну колонку `users.role` і перевіряти її на `POST /api/products`.

## Налаштування користувача

**Підхід:** колонка `users.settings` типу JSON з довільним об'єктом, наприклад:

```json
{ "language": "uk", "theme": "dark", "notifications": { "email": true, "push": false } }
```

`GET /api/users/me` повертає налаштування, `PATCH /api/users/me/settings` доповнює їх (`null` видаляє ключ). Доступ має лише сам користувач.

**Чому JSON, а не таблиця ключ-значення чи фіксовані поля:**

- Структура заздалегідь невідома і може бути вкладеною (`notifications`). Таблиця ключ-значення зберігає лише плоскі пари рядків.
- Налаштування завжди читаються цілком для одного користувача: один рядок, без JOIN.
- Типи значень зберігаються: `true` лишається булевим, а не рядком `"true"`.
- Нове налаштування не потребує міграції, на відміну від фіксованих полів.

Атрибути товарів, навпаки, зроблені окремою таблицею: їх додають по одному, і вони можуть знадобитися для фільтрації товарів. Мінус JSON — повільніший пошук за значенням. Якщо колись знадобиться, його можна прискорити генерованою колонкою з індексом.
